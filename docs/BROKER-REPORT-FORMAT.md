# Формат отчёта брокера: что показала разведка

Разбор **15 обезличенных отчётов за 2017–2020 годы** («ОТЧЕТ ПО СДЕЛКАМ И
ОПЕРАЦИЯМ С ЦЕННЫМИ БУМАГАМИ И ВАЛЮТНЫМИ ИНСТРУМЕНТАМИ…»). Это шаг 0 этапа 1:
форма документа, словарь операций, формы чисел и то, как всё это менялось за три
года.

Инструменты разбора: `tools/report_structure.py dump` и `compare`. Числа в
таблицах ниже — «в скольких отчётах из 14 встретилось» (пятнадцатый разбирался
отдельно и вошёл в выводы).

---

## 1. Это выгрузка из Excel, а не веб-страница

```
<meta name="ProgId" content="Excel.Sheet">
<meta name="Generator" content="Microsoft Excel 15">
```

Следствия, каждое из которых важно парсеру:

| Наблюдение | Что из этого следует |
|---|---|
| **Весь отчёт — одна таблица** `<table>`, 115 строк × 21 колонка | `find_sections` в `mapping_v1` ищет секции как **отдельные таблицы** и на этом отчёте находит одну безымянную. Секции здесь — строки внутри единственной таблицы |
| 270 `colspan` и 51 `rowspan` | без разворачивания объединений данные съезжают относительно шапки: «Место совершения сделки» из шапки стоит над «Дата поставки фактическая» в данных |
| Шапка секции сделок — **две строки**: основная плюс «Плановая / Фактическая» под объединёнными «Дата оплаты» и «Дата поставки» | одна логическая колонка занимает две физические; `resolve_columns` рассчитан на одну строку заголовков |
| Числовые ячейки несут атрибут `x:num` | в необезличенном отчёте там лежит **точное значение** отдельно от видимого текста. Для парсера — подарок (надёжный признак числа), для обезличивания — главная ловушка |
| `<style>` с правилами Excel внутри `<!-- -->` | `tables.py` затаскивает текст `<style>` в `preceding_text` первой таблицы: мусор в якорях |
| Два `<img>` | в боевом отчёте это логотип и, возможно, факсимиле подписи |
| Кодировка UTF-8 с BOM, переводы строк CRLF | `decode_report` справляется; BOM снимается |
| В архиве встречаются файлы в UTF-8 с метой `charset=windows-1251` | объявлению верить нельзя: CP1251 декодирует такой файл без ошибок и молча превращает текст в `РЎРѕСЃС‚РѕСЏРЅРёРµ`. Кодировка выбирается по качеству результата |
| Объявление кодировки бывает в двух формах: `<meta http-equiv="Content-Type">` и HTML5 `<meta charset>` | при выводе через libxml2 первая форма исчезает. Любой инструмент, переписывающий отчёт, обязан оставить объявление в HTML5-форме, иначе файл открывается мусором в браузере при исправных байтах |

## 2. Разделительные числовые форматы

| Что | Как выглядит | Замечание |
|---|---|---|
| Разделитель разрядов | обычный пробел (`1 234.56`), **не** `\xa0` | `parse_decimal` справляется, но фикстура должна содержать и этот вариант |
| Десятичный разделитель | **точка**, не запятая | то есть «русские числа» у этого брокера — пробел плюс точка |
| Знаков после точки | 0, 2, 3, 4 и **6** | по всему архиву: `0 000.00` (5601 раз), `00` (2117), `0 000.0000` (263), `0 000.000` (27), `0 000.000000` (10). Шесть знаков — курс валютной пары; округление до копейки потеряет цену |
| Отрицательные количества | `-00` (3 раза за архив) | количество бывает со знаком минус: короткая позиция или возврат займа |
| Отрицательные | `-1 234.56` | знак перед числом |
| Даты | `00.00.0000` (`дд.мм.гггг`) | время отдельной колонкой, `чч:мм:сс` |
| Номер сделки | `B-000000-000000` | буква, дефис, две группы цифр |
| Валюта | `RUR`, не `RUB` | в `formats._CURRENCY_ALIASES` уже есть |

номер гос. регистрации, валюта), затем сделки, затем `Итого по выпуску:` с
подстроками «оборот» и «изменение», затем `Общий итог:`. То есть **инструмент
сделки берётся не из её строки, а из подзаголовка группы** — принципиально иначе,
чем предполагает `mapping_v1`.

## 4. Словарь операций по архиву

Собран командой `report_structure.py compare архив/*.html`. Разбивка по секциям
принципиальна: одно и то же слово в денежной и в бумажной секции означает разные
события журнала.

### Денежные операции (8.1 и 8.1.1)

| Тип операции | Что это в журнале |
|---|---|
| `Ввод ДС` | `CASH_IN` |
| `Вывод ДС` | `CASH_OUT` |
| `Погашение купона` | `COUPON` |
| `Погашение номинала` | **выплата**: `MATURITY` или `AMORTIZATION` (A-20) |
| `Погашение облигации` | **маркер с нулевой суммой**, события не порождает (A-20) |
| `Доход по финансовым инструментам` | `DIVIDEND`; что это дивиденд, видно **только из комментария** |
| `Налог` | `TAX` |

### Операции с бумагами (8.2)

| Тип операции | Что это в журнале |
|---|---|
| `Ввод ЦБ` | перевод бумаг извне: `TRANSFER` без денежного эффекта |
| `Конвертация ЦБ` | `CONVERSION` — требует `predecessor_id` и переноса цены приобретения |
| `Погашение облигации` | списание бумаги при погашении |

Секция 8.2 — это **вторая сторона** событий: денег в ней нет, есть дата, тип,
бумага и количество. Колонки: `Дата | Тип операции | Наименование ЦБ | Номер гос.
регистрации | ISIN | Эмитент | Количество ЦБ | Комментарий`.

### Виды сделок (секции 5.*)

| Значение | Где встречается |
|---|---|
| `Покупка`, `Продажа` | 5.1, 5.10 |
| `Выдача займа ценных бумаг`, `Возврат займа ценных бумаг` | 5.4, 5.9 |
| `1-я часть`, `2-я часть` | `Тип сделки займа`, `Тип сделки РЕПО`, `Тип незавершенной сделки` |

**Погашение печатается тремя строками** на одну дату (A-20):

```
8.1.1  Погашение облигации   0.00        ← маркер, суммы нет
8.1.1  Погашение номинала    12 345.67   ← выплата, идёт в журнал
8.2    Погашение облигации   100 шт.     ← списание бумаги, идёт в журнал
```

Задвоения нет: наивное суммирование денежной секции ничего не испортит, потому
что первая строка нулевая. Но событие с нулевой суммой в append-only журнале —
шум, неотличимый потом от ошибки импорта, поэтому маркер отбрасывается.

**Займы бумаг** (5.4, 5.9) — это займ брокером у клиента: бумаги остаются в
собственности, позиция не меняется, выдача и возврат денег не двигают. В журнал
идёт только **вознаграждение за займ** — оно приходит в колонке `% по сделке`
строки «Возврат займа ценных бумаг» (2-я часть); у строки выдачи (1-я часть) эта
колонка пуста (A-21). Если допущение неверно, это проявится на бэкфилле
расхождением количества — сверка для того и нужна.

Место совершения: `Московская биржа (СПОТ: МБ T+)`,
`Московская биржа (МБ ФР: Т+: Корп. облигации)`, `OTC (Заем ОТС бумаги)`.

Полезные наблюдения:

* **дивиденд приходит как `Доход по финансовым инструментам`**, а что это именно
  дивиденд, сказано только в комментарии: «Выплата дивидендов, Акции
  обыкновенные ПАО "…", Рег. номер …, Дата регистрации …, Размер выплат на 1 ЦБ: …».
  Распознавать тип по колонке `Тип операции` недостаточно;
* **налог приходит отдельной строкой** — расщеплять gross/net не нужно, нужно
  связать `Налог` с его купоном или дивидендом. Связь восстанавливается только
  из комментария («Налог на доходы по дивидендам, 13%, Акции обыкновенные ПАО "…"»);
* **купон связан с бумагой только через комментарий**: «Погашение купона № RU000A105X64»
  — иногда ISIN, иногда краткое название («Погашение купона № Самолет БО-П13»,
  «№ ОФЗ 26219»). Значит разрешение инструмента по этому полю будет неточным и
  потребует справочника;
* комиссии в неторговых операциях не встретились: они сводятся в секции 1.1
  одной суммой за период по каждому виду. **Привязки комиссии к сделке нет в 8.1,
  но она есть прямо в строке сделки** (брокерская комиссия, комиссия ТС, гербовый
  сбор) — это лучше, чем предполагалось в `A-06`.

### Валюта — три разные колонки

В строке сделки **три** колонки валюты, и они не совпадают:

```
Цена одной ЦБ | Валюта цены | … | Сумма сделки | Валюта суммы сделки | Брокерская комиссия | Валюта брокерской комиссии
    0 000.0000 |     USD     | … |   0 000.00   |        RUR          |      0 000.00       |          RUR
```

Еврооблигация котируется в долларах, а рассчитывается в рублях. Одна колонка
«валюта» на всё означала бы, что долларовая сделка списывает доллары, — а
списывает она рубли. В архиве встречаются `RUR`, `USD`, `CNY`.

Отсюда же следует, что допущение A-08 (валюта по умолчанию) к секции сделок
неприменимо: валюта там всегда явная, вопрос только в том, какую из трёх брать.
Для денежного эффекта — `Валюта суммы сделки`.

## 5. Две даты

В строке сделки **четыре** даты: «Дата оплаты» плановая и фактическая, «Дата
поставки» плановая и фактическая. Плюс «Дата сделки». Это богаче модели из спеки
(`trade_date` и `settlement_date`):

* `trade_date` ← «Дата сделки»;
* `settlement_date` ← «Дата оплаты **фактическая**», а при её отсутствии
  (сделка ещё не рассчитана на дату отчёта) — плановая. Выбор нужно зафиксировать
  в `ASSUMPTIONS.md` (это уточнение к A-03: колонка есть, вопрос в том, какая из
  четырёх).

Остатки денежных средств печатаются в двух видах: «Исходящий остаток» и
«Исходящий **плановый** остаток (всего)». Для сверки по `settlement_date` нужен
первый; плановый включает незавершённые расчёты. Это тоже решение для реестра.

## 6. Что это значит для парсера

Текущий `mapping_v1` написан под гипотезу «секция = таблица» и на этом отчёте
даст одну неопознанную таблицу целиком. Нужен `mapping_v2` (или, точнее,
`mapping_excel_v1`) со следующими отличиями:

1. ~~**`tables.py` должен разворачивать `colspan`/`rowspan`** в сетку~~ —
   **сделано**: `RawTable` хранит ячейки с номерами колонок сетки, многострочная
   шапка склеивается в имя вида «Дата оплаты · Фактическая», а `as_dicts()`
   сопоставляет данные с шапкой по колонке, а не по порядковому номеру;
2. **якорение секций по строкам, а не по таблицам**: подпись секции — строка,
   данные секции — строки до следующей подписи;
3. **двухстроечные шапки**: объединённый заголовок плюс уточнение под ним
   («Дата оплаты» → «Плановая»/«Фактическая»);
4. **инструмент из строки-подзаголовка группы**, а не из строки сделки;
5. **связь налога и купона с инструментом из текста комментария**;
6. **восемь видов комиссий** из секции 1.1 плюс комиссии в строке сделки;
7. `<style>` не должен попадать в `preceding_text`;
8. `x:num` можно использовать как надёжный признак числовой ячейки.

Пункты 1–3 — изменения в стадии 1 парсера, то есть в том самом модуле, который
«меняется только при смене движка отчётов». Движок и оказался другим: не HTML-
страница, а выгрузка Excel. Это нормальный ход событий, ради которого стадии и
разделены: `money.py`, `domain/`, `jobs/` и CLI остаются как есть.
