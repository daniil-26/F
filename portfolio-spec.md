# Учёт инвестиций — описание функционала

Версия 0.1. Личный self-hosted инструмент учёта и анализа портфеля (российский рынок).

---

## 1. Рамки проекта

**Пользователь:** один человек, self-hosted, без авторизации и мультипользовательности.

**Источники операций:** один брокер, HTML-отчёты за месяц. Плюс ручной ввод через CSV.

**Что делает:** учёт активов, расчёт доходности, прогноз денежного потока, подбор облигаций, сверка план/факт.

### Вне периметра

- исполнение сделок и любая торговля;
- реальное время (достаточно дневного среза);
- налоговая отчётность как юридический документ (оценка налога — да, декларация — нет);
- бэктест стратегий;
- мобильное приложение.

---

## 2. Архитектура

Однонаправленный поток данных через слои:

```
Внешние источники (MOEX ISS, брокер, ЦБ РФ, рейтинги, CSV)
        ↓
Адаптеры          — единственное место, где живёт знание про HTTP/HTML/CSV
        ↓
Сырьё             — immutable, хеш файла, версия парсера
        ↓
Нормализация      — разрешение ID, валюты, шкалы; справочники
        ↓
Журнал операций   — append-only, идемпотентный
        ↓
Расчётное ядро    — чистые функции, без БД и сети
        ↓
Представление     — CLI (запись) и веб (чтение)
```

### Принципы

1. **Append-only.** Журнал не редактируется. Исправление — сторнирующая запись плюс новая.
2. **Состояние — производное.** Позиции, P&L, доходности вычисляются из журнала, а не хранятся как редактируемые таблицы.
3. **Сырьё сохраняется всегда.** Возможность переиграть историю новым парсером.
4. **Ядро без I/O.** Расчётные функции не знают про БД. Тестируются офлайн.
5. **Правило импорта — только вниз.** `calc` не знает про `adapters`, `domain` не знает про `web`.
6. **Деньги — только `Decimal` / `NUMERIC`.** Никогда `float`.
7. **Абстракция вводится на второй реализации.** Один брокер — один конкретный парсер, без плагинной системы.
8. **Отсутствие данных не подменяется нулём.** `None` и прочерк вместо правдоподобного числа. Подробнее — раздел 5.4.

## 3. Модель данных

### Журнал операций

Единая таблица событий для всех классов активов, включая вклады.

| Тип события | Внешний поток | Комментарий |
|---|---|---|
| `OPENING_BALANCE` | да | начальное состояние |
| `CASH_IN` | да | довнесение |
| `CASH_OUT` | да | изъятие |
| `TRANSFER` | да | между брокером и банком |
| `BUY` / `SELL` | нет | |
| `COUPON` | нет | доход портфеля |
| `DIVIDEND` | нет | доход портфеля |
| `AMORTIZATION` | нет | |
| `MATURITY` | нет | |
| `FX_CONVERT` | нет | |
| `FEE` / `TAX` | нет | |
| `DEPOSIT_OPEN` / `DEPOSIT_INTEREST` / `DEPOSIT_CLOSE` | нет | |

Классификация «внешний / внутренний» — свойство типа события, а не решение на лету. От неё зависит корректность всех доходностей.

Поля: `date`, `account_id`, `instrument_id`, `quantity`, `price`, `accrued_int`, `fee`, `amount`, `currency`, `cbr_rate`, `source_report_id`, `natural_key`, `recorded_at`, `reverses_id`.

**Идемпотентность:** `natural_key` = хеш от (счёт, дата, тип, инструмент, количество, цена, комиссия). Повторный импорт того же отчёта не задваивает.

### Начальный остаток

```
OPENING_BALANCE
  date            дата, с которой начинается учёт
  instrument_id   NULL для денег
  quantity
  cost_basis      цена приобретения, если известна
  basis_quality   known | estimated | unknown
  note            откуда взята цифра
```

При `basis_quality = unknown` система **не показывает** финрезультат и налоговую базу по позиции — только текущую стоимость. Прочерк вместо выдуманного числа.

Для расчёта доходности трактуется как внешний приток по рыночной цене на дату отсечки.

### Справочники

`issuers`, `instruments`, `prices_daily`, `bond_schedule`, `corp_actions`, `ratings`, `fx_rates`, `deposits`, `broker_tariff`.

**`broker_tariff`** — комиссия как структура, а не число: процент от оборота, минимум за сделку, депозитарная плата за месяц, комиссия за вывод, дата начала действия тарифа. Фактические комиссии из отчёта лежат в журнале, но для оценки стоимости **будущей** сделки нужен сам тариф. Из отчёта он не восстанавливается — заполняется вручную и меняется редко.

**Битемпоральность** для `ratings`, `corp_actions`, `bond_schedule`:
- `valid_from` / `valid_to` — когда факт был верен;
- `recorded_at` — когда мы о нём узнали.

Без второй оси невозможно ответить «какой был рейтинг на момент покупки» и невозможно честно сравнить прогноз с фактом.

### Ежедневный ряд

```
daily_nav
  date
  nav            стоимость всех активов на конец дня, ₽
  external_flow  сумма внешних потоков за день (+ приток)
```

Считается ночной джобой. Из этих двух рядов выводятся все метрики доходности — это гарантирует их согласованность между собой.

## 4. Функционал

### 4.1 Импорт брокерских отчётов

Парсер разделён на две стадии с разной стабильностью:

- **Структурная** (`adapters/broker/tables.py`) — достать все таблицы из HTML как есть. Не меняется годами.
- **Семантическая** (`adapters/broker/mapping_v1.py`) — отобразить таблицы на доменные события. Версионируется: при смене формата рядом появляется `mapping_v2.py`, предыдущая версия остаётся рабочей. Номер версии пишется в `raw_reports`.

Парсер — функция `bytes → (операции, остатки, нераспознанное)`. Он не сохраняет файл и не пишет в базу: этим занимается `jobs/import_broker.py`. Благодаря этому golden-тесты работают без БД и без сети.

Требования:
- таблицы якорятся по тексту заголовка, не по индексу;
- нормализация чисел на входе: неразрывный пробел как разделитель разрядов, запятая как десятичный;
- распознавание и отбрасывание строк «Итого» и подзаголовков;
- перекрытие периодов между отчётами решается идемпотентностью.

Остаток денежных средств берётся из таблицы остатков и используется как контрольная точка, а не выводится суммированием сделок.

**Комиссии разбираются по типам** (брокерская, депозитарная, за вывод), а не сводятся в одну сумму. Задним числом это восстанавливается только переимпортом всей истории, поэтому закладывается сразу.

**Поток импорта:**
1. загрузка файла, сохранение сырья, проверка хеша на дубль;
2. разбор → таблица операций: новые / уже существующие / нераспознанные;
3. сверка расчётных остатков против остатков из отчёта;
4. подтверждение — одна транзакция в БД.

При несошедшейся сверке подтверждение возможно, но требует явного флага, причина пишется в примечание к импорту.

### 4.2 Акции

- История котировок из MOEX ISS.
- История дивидендов (`/iss/securities/{secid}/dividends`) — только утверждённые. Прогноз вводится вручную из дивполитики.
- Учёт сплитов и консолидаций при пересчёте истории.
- **Сектор привязан к эмитенту, не к тикеру** — обыкновенные и привилегированные акции одного эмитента дают один риск.
- Метрики диверсификации: доли по секторам, индекс Херфиндаля, доля топ-5, группировка по конечному владельцу.

### 4.3 Облигации

Доходность не хранится как поле, а вычисляется функцией от графика платежей.

- **Полная цена** = `цена_% × номинал_на_дату / 100 + НКД`. Функция `face_value_at(secid, date)` учитывает амортизацию.
- **YTM, YTP, текущая доходность, XIRR по факту.** К оферте и к погашению считаются раздельно, обе показываются.
- **Флоатеры.** Купон известен только на текущий период. Прогноз требует сценария по ключевой ставке.
- **Валютные и замещающие.** Номинал в валюте, расчёт в рублях по курсу ЦБ на дату выплаты. Два P&L — в валюте и в рублях. Налоговая база в рублях, поэтому валютная переоценка создаёт налог даже при нулевой валютной доходности.
- **G-спред** — YTM минус интерполированная кривая ОФЗ той же дюрации.

**Скринер:** фильтры по рейтингу (единая числовая шкала), дюрации, наличию оферты, типу купона и **ликвидности** (объём и число сделок за 30 дней). Без фильтра ликвидности скринер выдаёт бумаги с нереализуемой доходностью.

Источники: `bondization` для купонов и амортизаций, доска торгов для текущих YTM и дюрации (как проверка собственного расчёта — расхождение более 5 б.п. означает баг в графике).

### 4.4 Вклады

Вводятся **условия**, а не график: сумма, ставка, дата открытия, срок, капитализация, пополняемость, база начисления, условия досрочного расторжения. График из 12–60 плановых событий генерируется.

Живут в общем журнале, не в отдельной подсистеме — иначе единый денежный поток не сойдётся.

**Налог считается по всем вкладам сразу за год:** суммарный процентный доход минус необлагаемый минимум (1 млн ₽ × максимальная ключевая ставка на 1-е число месяцев года), остаток по ставке НДФЛ. Показывается эффективная ставка после налога.

### 4.5 Рейтинги

Хранится история, не состояние. Изменение = закрытие предыдущей строки + вставка новой.

```
ratings
  entity_type    issuer | issue      ← разные сущности, могут расходиться
  entity_id
  agency         АКРА | Эксперт РА | НКР | НРА
  scale
  rating
  outlook
  action         присвоен | повышен | понижен | подтверждён | отозван
  valid_from     дата рейтингового действия
  valid_to       NULL пока действует
  recorded_at
  source_url
```

- Правило разрешения: рейтинг выпуска, при отсутствии — эмитента. Источник виден в интерфейсе.
- **Отзыв — это состояние, а не NULL.** Отозванный и отсутствующий означают разное.
- Несколько агентств хранятся все, для скринера сводятся в одно число (по умолчанию — минимум). Числовой маппинг шкал — приближение для сортировки, не утверждение о сопоставимости.

Что даёт: алерты по позициям, дрейф качества портфеля (рейтинг на момент покупки против текущего), средневзвешенный рейтинг во времени.

### 4.6 Доходность

**TWR** — очищена от довнесений, отвечает на вопрос о качестве выбора бумаг:

```
r_t  = (nav_t − flow_t) / nav_{t−1} − 1
TWR  = Π(1 + r_t) − 1
```

При дневном ряде разбиение на отрезки вырождается — каждый день свой отрезок. Приближения вроде Modified Dietz не нужны.

**MWR (XIRR)** — сколько заработали деньги с учётом момента внесения. Вектор: все внешние потоки плюс текущий `nav` как финальный приток.

Обе показываются рядом. Расхождение — информация о том, удачно ли выбирались моменты довнесений.

Требования:
- соглашение о моменте потока: конец дня, зафиксировано и не меняется;
- XIRR: брекетинг на `[-0.99, 10]` + метод Брента; при отсутствии решения — `None` и прочерк, не случайное число;
- **`external_flow` считается относительно выбранного среза.** Перевод из акций в облигации внутренний для портфеля, но внешний для облигационной части. Функция потока принимает предикат отбора позиций;
- изъятия не влияют на доходность;
- рядом с процентами показываются абсолютные числа: внесено / изъято / текущая стоимость / заработано.

### 4.7 Прогнозы и план/факт

Прогноз — **замороженный артефакт** `forecast_run` с датой создания и параметрами сценария, а не функция, пересчитываемая на лету. Иначе сравнение план/факт сравнивает факт с самим собой.

Сценарий задаёт траекторию ключевой ставки, курса и дивполитику. Для флоатеров и валютных бумаг сценарий обязателен.

Отклонение раскладывается на компоненты: курс, налог, досрочное погашение или оферта, изменение купона флоатера.

### 4.8 Сверка и входящие

Единая очередь всего, что требует внимания:
- строки отчёта, не прошедшие разбор;
- расхождения последней сверки остатков;
- изменения рейтингов по бумагам портфеля (диффом);
- приближающиеся оферты и погашения;
- вклады, закрывающиеся в ближайший месяц.

Сверка остатков — единственный механизм, отличающий «данные верные» от «данные выглядят правдоподобно».

### 4.9 Дашборд

- **Обзор.** Стоимость, TWR и XIRR, распределение по классам и секторам, ближайшие выплаты.
- **Календарь потока.** Столбики по месяцам на год вперёд: купоны, амортизации, погашения, дивиденды, закрытия вкладов. Зафиксированное и прогнозное разной заливкой.
- **Позиции.** Таблица с разворотом в карточку бумаги: график цены, сделки, график платежей, история рейтинга.
- **Скринер облигаций.**
- **План/факт.**
- **Входящие.**

## 5. Надёжность

Раздел обязательный к реализации. Всё перечисленное ниже строится **раньше** аналитики и дашборда, а не после.

Исходный принцип: надёжность — это не отсутствие ошибок, а их обнаруживаемость. Любая система ошибается; разница в том, узнаете ли вы об этом. Технология сама по себе обратную связь не создаёт — её нужно построить явно.

### 5.1 Классы ошибок и средства защиты

| Класс | Пример | Чем закрывается |
|---|---|---|
| Ввод | пропущена сделка, опечатка в количестве | сверка остатков с отчётом брокера |
| Формула | неверный YTM, TWR без учёта потока | юнит-тесты + сверка с внешними эталонами |
| Данные источника | не учтён сплит, взят биржевой курс вместо ЦБ | инварианты, проверки аномалий |
| Тихая деградация | парсер вернул пустоту, скрейпер сломался | контроль свежести данных |
| Непонимание предметной области | считается не то, что предполагалось | независимое ревью допущений |
| Потеря данных | | бэкапы, сохранённое сырьё |

Предпоследний класс инженерными средствами не закрывается: и код, и тест к нему пишутся из одного и того же представления. Ревью должно быть направлено на **предметные допущения** — классификация потоков, определение доходности, момент признания налога — а не только на код.

### 5.2 Инварианты

Проверяются в `revalue` и в `check`. Нарушение — **падение джобы с ненулевым кодом возврата**, а не запись в лог.

- сумма позиций по ценам равна `nav` за тот же день;
- денежный остаток из журнала равен остатку из последнего отчёта брокера;
- сумма купонов из графика за прошедший период равна сумме купонов в журнале;
- сумма сторнирующих записей и оригиналов по каждой скорректированной операции равна нулю;
- количество бумаг ни по одной позиции не отрицательно;
- `external_flow` за день равен сумме событий, помеченных как внешние, — без исключений и ручных поправок.

### 5.3 Контроль свежести данных

Отдельный класс проверок, потому что сломавшийся источник выглядит совершенно нормально: пустой список вместо цен не вызывает ошибки.

- `prices_daily` старше трёх торговых дней — алерт;
- курсы ЦБ старше двух дней — алерт;
- ни одного рейтингового события за месяц при непустом портфеле облигаций — алерт (вероятная поломка скрейпера);
- отчёт брокера за прошлый месяц не импортирован к 15-му числу — напоминание во «Входящие».

### 5.4 Запрет значений по умолчанию

Отсутствие данных не подменяется нулём **нигде**. Конструкция вида `.get(key, 0)` в расчётном контуре запрещена.

- нет цены на дату → `None` → прочерк в интерфейсе и исключение позиции из `nav` с явной пометкой;
- нет курса → расчёт не выполняется, а не выполняется по последнему известному;
- `basis_quality = unknown` → финрезультат и налоговая база не показываются;
- XIRR не сошёлся → прочерк, а не произвольное число.

Ноль, подставленный вместо отсутствующего значения, растворяется в сумме портфеля и уже никогда не обнаруживается.

### 5.5 Тесты

**Golden-тесты парсера.** Обезличенный реальный отчёт плюс зафиксированный ожидаемый результат в `tests/fixtures/`. Каждый найденный баг превращается в новую строку фикстуры. Самый ценный тест в проекте.

**Юнит-тесты расчётного ядра.** Возможны потому, что ядро чистое — ни БД, ни сети. Эталонные выпуски с известным ответом.

**Свойства (property-based, hypothesis)** для `money` и `bonds`:
- YTM бумаги без амортизации, купленной по номиналу, равна купонной ставке;
- цена монотонно убывает по доходности;
- парсинг числа и его форматирование взаимно обратны;
- сумма графика купонов не зависит от порядка обхода.

**Тест на сверку.** Импорт эталонного отчёта обязан давать нулевое расхождение остатков. Это регрессия на весь контур целиком.

### 5.6 Внешние эталоны

Готовые инструменты используются не как замена, а как независимая проверка. Расхождение считается багом до тех пор, пока не доказано обратное.

| Что проверяем | Эталон | Порог |
|---|---|---|
| YTM простых выпусков | калькулятор доходности Мосбиржи (фикс. купон, без оферт) | до копейки |
| YTM всех выпусков, дюрация | поля `YIELD`, `DURATION` с доски торгов ISS | 5 б.п. |
| TWR, XIRR | Portfolio Performance на тех же операциях | 0.1 п.п. |
| Позиции, остатки | отчёт брокера | точно |
| Календарь купонов на квартал | приложение брокера | точно |

Сверка с ISS оформляется командой и запускается регулярно, а не разово: это непрерывный тест на реальном портфеле.

### 5.7 Параллельный прогон

**Переключение с существующих Excel-файлов происходит не раньше, чем через три месяца параллельной работы.**

Каждый месяц сравниваются итоговые числа обеих систем, каждое расхождение разбирается до причины. Часть расхождений окажется ошибками старых таблиц — это и есть эмпирическое подтверждение готовности.

Досрочное переключение запрещено правилом проекта: полусобранная система с доверием как к готовому продукту опаснее, чем таблица, про которую известно, что она приблизительная.

### 5.8 Сохранность

- `pg_dump` по расписанию, восстановление проверяется хотя бы раз;
- каталог `data/raw/` с исходными HTML — резервная копия отдельно от БД;
- CSV-входы под git;
- проверка: система должна полностью восстанавливаться из `data/raw/` + `data/input/` + код. Если это не так — где-то есть данные, существующие только в БД, и их нужно вынести.

### 5.9 Порядок реализации

Из раздела следует жёсткое ограничение на этапы: **сверка остатков и инварианты реализуются на первом этапе, вместе с импортом**. Аналитика, скринер и дашборд не начинаются, пока `portfolio check` не проходит на реальных данных.

Без этого получится Excel на PostgreSQL: те же непроверяемые числа, но с бо́льшим доверием к ним.

## 6. Интерфейсы

**Запись — CLI и CSV. Чтение — веб.**

### CSV под контролем версий

Файлы описывают **желаемое состояние**, а не события. Импортёр диффит файл с журналом и сам генерирует сторнирующие записи. Исправление ставки в строке файла превращается в сторно плюс новую запись без отдельного UI для правок.

```
deposits.csv           вклады: условия
cash_flows.csv         довнесения и изъятия
opening_balances.csv   начальные остатки
sector_overrides.csv   ручная классификация секторов
```

Лежат в git рядом с кодом: история изменений, читаемый дифф, бэкап через `git push`.

Валидация через pydantic с сообщениями вида «строка 14, поле rate: ожидалось число».

### CLI

```
portfolio import-broker report_2026-08.html [--dry-run]
portfolio import-csv deposits.csv [--dry-run]
portfolio sync-moex [--full]
portfolio sync-ratings
portfolio revalue              пересчёт daily_nav и проекций
portfolio inbox [--export pending.csv]
portfolio check                сверка остатков и инварианты; код возврата ≠ 0 при расхождении
portfolio check-freshness      свежесть цен, курсов, рейтингов
portfolio verify-yields        свои YTM против биржевых с доски ISS
portfolio export-pp            выгрузка операций в формат Portfolio Performance
```

Команды `check`, `check-freshness` и `verify-yields` запускаются по cron. Ненулевой код возврата — уведомление.

`--dry-run` печатает таблицу изменений и ничего не пишет.

Очередь подтверждений работает через те же файлы: `inbox --export` выгружает записи, вы правите колонку решения, `import-csv` применяет.

Те же команды используются человеком и планировщиком — одна кодовая база.

### Веб (только чтение)

Streamlit. Никакой записи, никаких мутаций — все ограничения, связанные с перезапуском скрипта и защитой от случайных изменений, снимаются вместе с формами ввода.

Правила:
- **в интерфейсе нет бизнес-логики** — страница вызывает функцию ядра или читает готовую проекцию;
- ничего тяжёлого в рендере: cron считает проекции, приложение делает простые `SELECT`;
- кеш инвалидируется по версии журнала (максимальный `id` в ledger), не по TTL;
- `Decimal` форматируется в строку на границе вывода.

Причина выбора: скринер и карточка бумаги должны вызывать расчётное ядро на Python. В BI-инструменте пришлось бы переписать YTM и доходности на SQL, то есть завести вторую реализацию тех же формул.

## 8. Этапы

1. **Журнал, импорт, сверка, инварианты, golden-тесты парсера.** Всё вместе, это один этап. Пока `portfolio check` не проходит на реальных данных — дальше не двигаться.

### `src/portfolio/` — корневые модули

| Файл | Функционал | Чего здесь нет |
|---|---|---|
| `config.py` | чтение `.env`, пути, константы (ставка НДФЛ, пороги сверки, лимит запросов к ISS) | логики |

### `calc/` — чистые функции

Не импортирует ничего из `adapters/`, `domain/`, `web/`. Ни БД, ни сети, ни времени «сейчас» — текущая дата всегда приходит аргументом. Проверяется линтером и `mypy --strict`.

| Файл | Функционал |
|---|---|
| `money.py` | тип `Money` = (`Decimal`, валюта); конструктор запрещает `float`. Арифметика с проверкой валют. `convert(money, rate, target)` — курс приходит аргументом. Правила округления: суммы до копейки, доходности до б.п., округление только на выводе. Распределение суммы на N частей без потери остатка (метод наибольшего остатка). `is_close` с допуском для сверки |
| `bonds.py` | `face_value_at` — номинал с учётом амортизации. `accrued_interest` — НКД. `full_price`. `future_cashflows` — построение будущего потока. `ytm` / `ytp` — солвер Брента на `[-0.99, 10]`, при отсутствии решения `None`. `duration`, `modified_duration`. `g_spread` |
| `returns.py` | `twr` по рядам `nav` и `external_flow`. `xirr` по вектору внешних потоков. Предикат отбора позиций для расчёта потоков по срезу портфеля |
| `deposits.py` | развёртка условий вклада в график начислений: капитализация, перенос на рабочие дни, база факт/365 |
| `tax.py` | НДФЛ по купонам и дивидендам. Налог на вклады: агрегация по году, необлагаемый минимум, прогрессивная ставка. Оценка налога при продаже |

Вся сложность облигаций — в `future_cashflows`, а не в солвере. Расхождение с биржевой YTM почти всегда означает ошибку в графике платежей.

### `adapters/` — внешний мир

Единственное место, где живёт знание про HTTP, HTML и форматы файлов. Не пишут в БД, не разрешают идентификаторы, ничего не считают. Возвращают DTO.

| Файл | Функционал |
|---|---|
| `formats.py` | разбор строк источников: русские числа (неразрывный пробел, запятая), даты, валюты. Используется и HTML-парсером, и CSV. В `calc/` не нужен |
| `broker/tables.py` | стадия 1: `bytes` → список таблиц как есть (заголовки, строки, ячейки строками). Не знает про сделки. Меняется, только если брокер сменит движок отчётов |
| `broker/anchors.py` | соответствие «текст заголовка секции → логическое имя». Поиск таблиц по подписи, не по индексу. При смене формулировки правится одна строка |
| `broker/mapping_v1.py` | стадия 2: таблицы → события. Отображение колонок, распознавание типа операции, отбрасывание строк «Итого». Версионируется: `mapping_v2.py` пишется рядом, v1 остаётся рабочим |
| `broker/dto.py` | `ParsedOperation`, `ParsedBalance`, `UnparsedRow`. Тикер и валюта строками, без `instrument_id` и `natural_key` |
| `moex.py` | ISS: котировки, дивиденды, `bondization`, доска торгов. Retry, `iss.meta=off`, лимит запросов, дисковый кеш |
| `cbr.py` | курсы валют, ключевая ставка, RUONIA |
| `ratings.py` | получение рейтинговых действий, приведение к единой структуре |
| `csv_input.py` | чтение и валидация входных CSV через pydantic. Ошибки вида «строка 14, поле rate: ожидалось число» |

Парсер отчёта — функция `bytes → (операции, остатки, нераспознанное)`. Она не сохраняет файл и не пишет в базу, поэтому golden-тесты работают без БД и без сети.

### Правила

- `models.py` одним файлом, пока не станет неудобно.
- Направление импортов: `web` → `jobs` → `domain` → `calc`; `adapters` → `calc`. Обратных импортов нет, проверяется линтером.
- Транзакции открываются только в `jobs/`.
- `calc/` не знает текущей даты: всё, что зависит от «сегодня», принимает дату аргументом. Иначе тесты станут зависеть от дня запуска.

## Приложение. Отложенные и спорные решения

Вещи, которые могут поменяться в процессе. Не закладывать заранее, но помнить о них при проектировании границ.

**Сценарии по ключевой ставке.** Начать с константы — купон флоатера не меняется до погашения. Полноценные сценарии (базовый / рост / снижение) добавить, когда флоатеры составят заметную долю портфеля.

**Источник рейтингов.** Начать с полуручного: джоба обходит страницы эмитентов портфеля, диффит с последним состоянием, кладёт изменения во «Входящие». Платный структурированный фид подключается заменой одного адаптера. Проверить условия использования сайтов агентств до автоматизации.

**Секторная классификация.** Начать с ручного `sector_overrides.csv` — при 20–40 бумагах это полчаса работы. Автоматика через отраслевые индексы MOEX покрывает только индексные бумаги и всё равно потребует ручных дополнений.

**Формат `cash_flows.csv`.** Декларативный (весь список, файл растёт) против событийного (дописывается, не пересматривается). При десятках строк в год первый вариант проще и надёжнее. Пересмотреть, если файл станет неудобным.

**Налоговый модуль.** Начать с оценки налога по купонам и вкладам. ЛДВ, ИИС-3, сальдирование убытков, FIFO для оценки налога при продаже — по мере необходимости.

**FIFO.** Нужен для оценки налоговой базы при планируемой продаже. В первой версии можно ограничиться средней ценой для отображения и не показывать потенциальный налог.

**Metabase рядом с Streamlit.** Для ad-hoc запросов к БД без правки кода. Как дополнение, не как замена — бизнес-логика остаётся в Python.

**TimescaleDB.** При объёмах в десятки тысяч строк цен обычного Postgres хватает с большим запасом. Рассматривать только если появятся внутридневные данные.

**Второй брокер.** Абстракция адаптеров появится сама при второй реализации. До этого — конкретный парсер без интерфейсов.

**Метрики риска.** Вклад в риск через ковариацию, корреляции между позициями — полезнее долей в портфеле, но требуют года истории доходностей. Отложить до момента, когда история накопится.

**Уведомления.** Telegram-бот для алертов «Входящих» вместо ручного захода в интерфейс. Тонкий слой поверх `portfolio inbox`.

### Слой поддержки решений

Задачи вида «какой актив продать», «как часто реинвестировать купоны», «вложить сейчас или подождать». Появляется как `calc/decisions.py` плюс страница в вебе.

**Ключевой принцип: считать точку безразличия, а не оптимум.** Вместо «выгоднее вложить сейчас» система отвечает «ожидание месяца оправдано, только если ставка вырастет более чем на 1.4 п.п.». Порог считается точно, прогноза не требует, решение остаётся за человеком. Оптимизатор же выдаёт число, за которым спрятана ваша собственная гипотеза, и создаёт ложное ощущение объективности. Правило: **если результат меняется от подставленного прогноза, показывать не результат, а границу переключения**.

Три задачи по возрастанию сложности:

- **Что продать.** Для каждого способа получить нужную сумму: комиссия по тарифу, реализованный налог по конкретным лотам, потерянный НКД или ближайший купон, штраф по вкладу. Издержки делятся на немедленные (считаются точно) и альтернативные (упущенная доходность — прогноз), показываются раздельно. Часто немедленных достаточно для решения. Неочевидный результат, ради которого стоит считать: иногда выгоднее продать позицию в убытке — он сальдируется с прибылью года.
- **Частота реинвестирования.** Одно уравнение: издержка ожидания (накопленная сумма × доходность × время простоя) против комиссии с учётом минимума. Результат — порог в рублях. Если свободные деньги лежат в фонде денежного рынка, порог заметно выше.
- **Сейчас или позже.** Вычислительно тривиально, вся работа в подаче результата.

**Когда закладывать.** Разделяется на две части. Данные — сразу, на этапах 1–3: `broker_tariff`, разбор комиссий по типам, лоты в `positions.py`, заполненные условия досрочного расторжения в `deposits.csv`. Это не функционал, а полнота учёта, и задним числом восстанавливается плохо. Сам слой — после этапа 6: он стоит на `tax.py`, `deposits.py`, `future_cashflows` и лотах, и пока они не сверены с эталонами, будет выдавать уверенные неверные ответы.

Объём при готовом ядре — около недели.

**Чего не делать:** портфельной оптимизации, Монте-Карло, подбора весов по эффективной границе. Результат целиком определяется предположениями о доходностях и корреляциях, которых вы не знаете.

**Аудит решений.** Записывать не только расчёт, но и принятое решение с отвергнутой альтернативой. Через год страница «принятые решения» покажет, что получилось бы в каждом случае. Единственный способ узнать, помогает этот слой или оформляет задним числом уже принятые решения. Ложится на существующие `forecast_runs`.

### Ключевая ставка и инфляция

Ключевая ставка уже нужна раньше — для флоатеров и для необлагаемого минимума по вкладам, адаптер `cbr.py` её забирает с этапа 2. Отложенное здесь — **исторические ряды и их использование в анализе**.

- ряд ключевой ставки с датами заседаний;
- ИПЦ Росстата: месячный и накопленный за 12 месяцев;
- инфляционные ожидания, если понадобятся.

Зачем: **реальная доходность** вместо номинальной. Портфель, выросший на 14% при инфляции 9%, и портфель, выросший на 14% при инфляции 4%, — разные результаты, а на дашборде выглядят одинаково. Достаточно одной дополнительной линии рядом с TWR.

Второе применение — контекст на графиках: заседания ЦБ как вертикальные отметки объясняют изломы доходности облигаций лучше любого текста.

Источники: ЦБ РФ для ставки, ЕМИСС или Росстат для ИПЦ. Отдельная таблица `macro_series` (ряд, дата, значение) — универсальная, чтобы не заводить по таблице на показатель.

### Парсинг предложений по вкладам

Сбор ставок по открытым предложениям банков для сравнения с текущими вкладами и для расчёта выгоды досрочного перекладывания.

Осложняющие обстоятельства, из-за которых это стоит в отложенных:

- витрины агрегаторов активно защищаются от автоматического сбора, условия использования нужно проверять отдельно;
- заявленная ставка почти всегда максимальная и обусловлена набором условий (новые деньги, подписка, зарплатный проект, оборот по карте). Число без условий бесполезно и вводит в заблуждение;
- предложения меняются быстрее, чем всё остальное в системе.

Разумный минимум вместо полноценного парсинга: **ручной ввод отслеживаемых предложений в `deposit_offers.csv`** — банк, ставка, срок, условия, дата проверки. Десяток строк, обновляется раз в месяц за пять минут. Даёт 90% пользы при нулевом риске.

Полезный автоматический источник, не требующий парсинга витрин: публикуемая ЦБ максимальная процентная ставка по вкладам в крупнейших банках. Это ориентир рынка, а не предложение, но для вопроса «текущий вклад отстал от рынка или нет» его достаточно.

Отдельно стоит контроль страхового лимита АСВ по каждому банку — он не требует никакого парсинга и полезнее ставок.

### Детерминированный прогноз доходности

Построение ожидаемой траектории портфеля из **текущих рыночных данных**, без предположений о будущем.

Идея: рынок уже содержит прогноз, его не нужно придумывать. Из кривой доходности ОФЗ выводятся **вменённые форвардные ставки** — какую ставку рынок закладывает на год начиная через год. Это арифметика по текущим ценам, а не мнение.

Что строится:

- кривая бескупонной доходности ОФЗ по срокам (Мосбиржа публикует КБД, можно и считать самостоятельно из цен);
- лестница ставок по вкладам разной длительности из того же `deposit_offers.csv`;
- вменённые форварды из обеих кривых;
- сопоставление: спред между депозитной и облигационной кривой на каждом сроке показывает, где сейчас платят больше за тот же горизонт.

Прикладной результат — прогноз денежного потока и стоимости портфеля на горизонте при условии реинвестирования по текущим рыночным ставкам. Прогноз детерминированный, и это надо подписывать явно: **не предсказание, а «что будет, если рынок окажется прав»**.

Отсюда же напрямую берутся точки безразличия для слоя решений: разница между текущей ставкой вклада и форвардной на тот же срок и есть цена ожидания.

Требует: кривую ОФЗ, лестницу депозитных ставок, `future_cashflows`. Реализуется после слоя решений и питает его.
