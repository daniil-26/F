# Реестр допущений

Каждое предметное решение — с идентификатором, датой вступления в силу и списком
затронутых модулей (спека 5.9). Код ссылается на идентификаторы в комментариях.

Статусы:

* **подтверждено** — решение проверено на реальных данных или не зависит от них;
* **требует подтверждения** — решение принято, чтобы код существовал, но должно
  быть перепроверено на архиве отчётов в шаге 0 этапа 1. До этой проверки
  считать его гипотезой, а не фактом.

Раздел 5.1 спеки признаёт, что непонимание предметной области инженерными
средствами не закрывается. Ревью направляется сюда, а не на код.

## A-01 Построение `natural_key`

Ключ идемпотентности строится в порядке предпочтения: номер сделки брокера;
иначе хеш от (счёт, дата сделки, тип, инструмент, количество, цена, сумма, вид
комиссии) плюс порядковый индекс внутри группы одинаковых операций. Индекс
считается **в пределах календарного дня, а не отчёта**.

Известный отказ (спека 3.2): отмена брокером одной сделки из группы сдвигает
индексы последующих и даёт ложное расхождение при диффе. Поэтому номер сделки
предпочтителен, и его наличие в отчёте надо подтвердить.

```
Действует с: 2026-09-11
Статус:      требует подтверждения (есть ли номер сделки во всех отчётах архива)
Затрагивает: domain/events.py, adapters/broker/mapping_v1.py
```

## A-02 Сплиты пишутся событием, а не применяются проекцией

`SPLIT` — событие журнала с дельтой количества; `positions.py` его просто
суммирует. Альтернатива (применять сплит проекцией при расчёте) чище, но тогда
сверка с отчётом брокера должна идти в пост-сплитных единицах, а отчёт печатает
фактические количества на дату.

## A-03 Дата расчётов при отсутствии колонки

Если в отчёте нет отдельной даты расчётов, `settlement_date` считается равной
`trade_date`. Вывод даты из торгового календаря (T+1) **не делается**: календарь
— справочник этапа 2, а угаданная дата расчётов ломает сверку денег ровно в тех
случаях, ради которых две даты и заведены.

```

Затрагивает: adapters/broker/mapping_v1.py, domain/positions.py
```

## A-04 Расщепление gross/net по купонам и дивидендам

Если в строке отчёта есть отдельная сумма налога, в журнал пишется сумма до
налога, а удержание — отдельным событием `TAX`; `withheld_at_source = false`.

Если суммы налога в отчёте нет, `withheld_at_source` остаётся `None` —
«неизвестно». Восстанавливать gross делением на (1 − ставка) **запрещено**: при
прогрессивной шкале это даёт неверное число, неотличимое от верного (спека 3.2).

```
Действует с: 2026-09-11
Статус:      требует подтверждения (купоны в отчёте брутто или нетто)
Затрагивает: adapters/broker/mapping_v1.py, domain/ledger.py
```

## A-05 Знаки количества и суммы

`quantity` — изменение позиции: покупка со знаком плюс, продажа со знаком минус.
`amount` — изменение денежного остатка: приход плюс, расход минус.

Обе проекции получаются суммированием без ветвлений по типу события. Ветвление
«если продажа, то вычесть» пришлось бы повторять в каждой проекции, и рано или
поздно оно где-то разошлось бы.

```
Действует с: 2026-09-11
Статус:      подтверждено (внутреннее соглашение, от данных не зависит)
Затрагивает: models.py, domain/positions.py, adapters/broker/dto.py
```

## A-06 Комиссии — отдельные события

Каждая комиссия пишется отдельным событием `FEE` со своим `fee_kind`
(брокерская, депозитарная, биржевая, за вывод). Поле `fee` у самой сделки
заполняется справочно и в денежный остаток **не входит** — иначе комиссия
посчиталась бы дважды.

Справочное поле нужно слою поддержки решений: «во что обойдётся продажа этой
позиции» требует комиссии, отнесённой к конкретной сделке, а задним числом это
не восстанавливается.

```
Действует с: 2026-09-11
Статус:      подтверждено (внутреннее соглашение)
Затрагивает: adapters/broker/mapping_v1.py, domain/ledger.py, models.py
```

## A-07 Денежный эффект сделки

Денежный эффект сделки = сумма сделки из отчёта ± НКД. НКД прибавляется **только
если он приходит отдельной колонкой**: наличие колонки означает, что брокер
показывает сумму сделки без него. Комиссии в сумму сделки не входят (A-06).

Сумма берётся из отчёта, а не считается как `количество × цена`: это
авторитетное число брокера, включающее его собственное округление. Расчёт
применяется, только когда колонки суммы нет.

```
Действует с: 2026-09-11
Статус:      требует подтверждения (входит ли НКД в сумму сделки)
Затрагивает: adapters/broker/mapping_v1.py
```

## A-08 Валюта по умолчанию

Если в таблице отчёта нет колонки валюты, операция считается рублёвой.

Это единственное место, где подставляется значение по умолчанию, и оно касается
не суммы, а её единицы измерения: отчёт российского брокера без колонки валюты
рублёвый. Как только в архиве найдётся валютная секция без колонки валюты,
допущение отменяется в пользу `UnparsedRow`.

```

Статус:      требует подтверждения (есть ли валютные секции без колонки валюты)
Затрагивает: adapters/broker/mapping_v1.py
```

## A-11 Начальный остаток — внешний приток

`OPENING_BALANCE` классифицируется как внешний поток. Для расчёта доходности он
трактуется как внешний приток по рыночной цене на дату отсечки (спека 3).

При `basis_quality = unknown` финрезультат и налоговая база по позиции не
показываются — прочерк вместо выдуманного числа.


## Решения, ожидающие шага 0

Шаг 0 этапа 1 (разведка отчёта) выполняется человеком на реальном архиве. До
него закрыты только те решения, без которых не существует кода. После разведки
статусы «требует подтверждения» пересматриваются, а несовпавшие допущения
исправляются в `mapping_v1` с переимпортом архива.

| Вопрос шага 0 | Допущение | Что меняется, если гипотеза неверна |
|---|---|---|
| Есть ли номер сделки брокера | A-01 | схема ключа и устойчивость к отменам сделок |
| Есть ли дата расчётов | A-03 | сверка денег на границе месяца |
| Купоны gross или net | A-04 | правило расщепления, оценка налога |
| Комиссии одной суммой или по типам | A-06 | возможность разбора; задним числом не восстановить |
| Входит ли НКД в сумму сделки | A-07 | денежный остаток по облигационным сделкам |
| Какие типы операций есть за всю историю | — | объём `mapping_v1` |
