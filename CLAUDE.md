# Личный учёт инвестиций — рабочая памятка агента

Самостоятельный учёт российского брокерского портфеля: журнал операций, импорт
отчётов брокера, сверка. Полная постановка — [`docs/portfolio-spec.md`](docs/portfolio-spec.md),
план текущего этапа — [`docs/STAGE-1.md`](docs/STAGE-1.md).

## Язык

**Общение с владельцем — по-русски. Комментарии, docstring, документация и
сообщения коммитов — по-русски.** Имена в коде — английские.

Комментарий объясняет **почему**, а не что: «что» видно из кода. Русский
комментарий, объясняющий неочевидное решение, здесь ценнее аккуратной
английской тавтологии.

## Команды

```bash
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"

pytest                          # 402 теста, без сети и без PostgreSQL
ruff check src tests tools scripts
mypy                            # весь пакет
mypy --strict src/portfolio/calc  # расчётное ядро — отдельно и строго
python tests/update_golden.py   # пересоздать эталоны, только осознанно
```

CLI (после `pip install -e .`):

```bash
portfolio init-db                       # схема в локальном SQLite
portfolio import-csv opening_balances.csv
portfolio import-broker архив/ -r       # каталог в хронологическом порядке
portfolio check                         # сверка после каждого месяца
portfolio inbox                         # нераспознанное и расхождения
```

Локальный прогон без сервера: `DATABASE_URL=sqlite:///portfolio.db` плюс
`portfolio init-db`. Схема PostgreSQL — только через `alembic upgrade head`.

## Архитектура: что нельзя нарушать

```
adapters/ → domain/ → jobs/ → cli.py        calc/ — чистые функции
```

* направление импортов проверяется `tests/test_layering.py` (разбор AST, не
  соглашение): `jobs → domain → calc`, `adapters → calc`;
* **транзакции только в `jobs/`**. `session_scope()` и `.commit()` в других
  слоях — падение теста;
* `calc/` не импортирует `sqlalchemy`, `httpx`, `psycopg` и не зовёт
  `date.today()`: время и хранилище приходят параметрами;
* `adapters/` возвращают DTO и **не пишут в БД**.

## Предметные правила, которые ломают данные, если их нарушить

* **Деньги — только `Decimal`.** Тип `Money` отвергает `float` на входе. Это не
  вкусовщина: `0.1 + 0.2` в учёте — расхождение сверки;
* **Журнал append-only.** Исправление — сторно плюс новая запись, никогда не
  `UPDATE` и не `DELETE`;
* **Идемпотентность по `natural_key`** (A-01), UNIQUE в БД. Повторный импорт
  того же отчёта обязан не менять журнал;
* **Две даты**: позиции по `trade_date`, деньги по `settlement_date` (A-03);
* **Суммы gross**, налог — отдельным событием `TAX` (A-04). Восстанавливать
  gross делением на (1 − ставка) запрещено;
* **Комиссии — отдельные события `FEE` по видам** (A-06), поле `fee` справочное;
* **Нет данных ≠ ноль.** Непонятая строка идёт в `UnparsedRow` и во «Входящие»,
  а не записывается нулём и не пропускается молча.

## Разбор отчёта брокера

Три стадии, версия выбирается по форме документа в `adapters/broker/mapping.py`:

| Модуль | Что делает |
|---|---|
| `broker/tables.py` | стадия 1: `bytes` → таблицы с разворачиванием `colspan`/`rowspan` |
| `broker/sections.py` | стадия 1.5: плоская выгрузка Excel → нумерованные разделы |
| `broker/anchors.py` | словари подписей: `COLUMNS` (v1) и `COLUMNS_V2` (реальный формат) |
| `broker/mapping_v1.py` | стадия 2 для формата «секция = таблица» (синтетические фикстуры) |
| `broker/mapping_v2.py` | стадия 2 для реального архива: выгрузка Excel одной таблицей |

Обе версии остаются рабочими: архив содержит файлы обоих форматов, применённая
версия пишется в `raw_reports.parser_version`.

## Текущее состояние

**Этап 1 завершён.** Весь архив отчётов импортирован в хронологическом порядке,
`check` возвращает ноль после каждого месяца, нераспознанных строк нет ни в
одном отчёте. Это и был критерий готовности этапа (`docs/STAGE-1.md`).

Что закрыл прогон по реальному архиву — по порядку, как вылезало:

| Находка | Где записана |
|---|---|
| `TRANSFER` не двигал позицию: «Ввод/Вывод ЦБ» писались в журнал, но проекция их не видела | `domain/positions.py` |
| первый токен подзаголовка группы сделок — внутренний код выпуска формы ISIN, а не ISIN бумаги | A-23 |
| вознаграждение за заём — сумма в рублях в «% по сделке» строки возврата; тип события `LENDING_INCOME` | A-21, A-24, миграция `0003` |
| контрольное количество бумаг — «Плановое количество ЦБ», а не «на конец периода» | A-26 |
| копеечные расхождения в месяцах с займом: мягкий допуск, но расхождение остаётся видимым | A-27 |
| `UNIQUE(ticker)` в схеме неверен: бумагу определяет ISIN, наименование её подписывает | A-28, миграция `0004` |
| у списываемой стороны конвертации ISIN не напечатан — бумага восстанавливается из комментария | A-29 |

Допущения A-04 (купон брутто) и A-07 (НКД вне «Суммы сделки») подтверждены
**косвенно**: будь любое из них неверно, денежный остаток разошёлся бы ровно на
сумму налога или НКД соответствующего месяца. Проверка годна настолько,
насколько в архиве встречались такие операции; строки для её повторения печатает
`tools/report_structure.py parse`.

Разрыв рабочего цикла (вывод прогона содержит настоящие суммы и потому не
показывается агенту) закрыт не полностью, но обошёлся: диагностика делается
командой `parse`, из которой владелец приносит форму расхождения, а не данные.
`inbox --digest` так и не понадобился.

## Правила работы

* **ветка** `claude/portfolio-stage-1-7qmcwq`, коммиты по-русски: что сделано и
  **почему именно так**;
* перед коммитом: `pytest`, `ruff check`, `mypy` — все зелёные. Тесты не
  «поправляются под код»;
* **golden-эталоны не переписываются молча.** `update_golden.py` запускается
  только после осознанной правки парсера, и изменение эталона объясняется в
  коммите;
* **реальные данные владельца в репозиторий не попадают.** Фикстуры —
  синтетические либо обезличенные `tools/anonymize_report.py`; настоящие отчёты
  живут вне git;
* новое предметное решение → запись в `ASSUMPTIONS.md` с обоснованием и тем, как
  оно проверится;
* новая зависимость — только с обоснованием: расчётное ядро обязано оставаться
  чистым Python.

## Грабли, на которые уже наступали

* **Кодировка.** Объявлению `charset` в отчёте верить нельзя: файл в UTF-8 с
  метой `windows-1251` читается как CP1251 без ошибок и превращается в
  «РЎРѕСЃС‚РѕСЏРЅРёРµ». Кодировка выбирается по качеству результата
  (`garbage_ratio`), а не по объявлению;
* **libxml2 выбрасывает `<meta http-equiv="Content-Type">`** при сериализации.
  Любой инструмент, переписывающий отчёт, обязан оставить объявление в
  HTML5-форме `<meta charset="utf-8">`, иначе браузер покажет мусор при
  исправных байтах;
* **`pip install .` вместо `-e .`** — импорт берёт старый снимок из
  `site-packages`, новые модули «не находятся». Проверка:
  `python -c "import portfolio.cli as c; print(c.__file__)"`;
* **SQLite в тестах** требует `BigInteger().with_variant(Integer, "sqlite")` для
  автоинкремента и `length(currency) = 3` вместо `char_length`;
* **Кириллица в консоли Windows** ломает сообщения PostgreSQL — это кодировка
  консоли, а не баг проекта.
