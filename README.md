# Учёт инвестиций

Личный self-hosted инструмент учёта и анализа портфеля (российский рынок).
Описание функционала — [`docs/portfolio-spec.md`](docs/portfolio-spec.md),
техническое описание реализованного — [`docs/IMPLEMENTATION.md`](docs/IMPLEMENTATION.md),
разбор формата отчёта брокера — [`docs/BROKER-REPORT-FORMAT.md`](docs/BROKER-REPORT-FORMAT.md),
краткая памятка для работы над проектом — [`CLAUDE.md`](CLAUDE.md).

**Этап 1 завершён:** журнал операций, импорт отчётов брокера, сверка остатков,
инварианты, golden-тесты парсера. Весь архив отчётов импортирован, `check`
возвращает ноль после каждого месяца. Рабочий план и итог этапа —
[`docs/STAGE-1.md`](docs/STAGE-1.md).

Ключевое свойство этапа: **ни одного сетевого запроса**. Сверка сравнивает
количества бумаг и денежный остаток, а не стоимость, поэтому весь этап
детерминирован и тестируется офлайн.

Параллельно с этапом 1 идёт независимый трек по облигациям
([`docs/PARALLEL-TRACK.md`](docs/PARALLEL-TRACK.md)): расчёт доходностей и
справочные данные MOEX ISS. Он не касается журнала и потому не ждёт прохождения
`check` — см. [«Облигации»](#облигации) ниже.

## Быстрый старт

```bash
cp .env.example .env
docker compose up -d db          # PostgreSQL
python -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
alembic upgrade head             # схема журнала
```

**Без PostgreSQL — локальный прогон на SQLite.** Сервер нужен для боевой
установки; чтобы просто прогнать архив у себя, достаточно указать файл БД:

```bash
# Windows (cmd)                    # Linux / macOS
set DATABASE_URL=sqlite:///portfolio.db
portfolio init-db                  # схема из тех же метаданных, что и в тестах
```

`init-db` работает только для SQLite. Схему PostgreSQL создаёт `alembic upgrade
head`: у боевой БД должна быть воспроизводимая история изменений.

Дальше — порядок, в котором данные попадают в журнал:

```bash
# 1. Начальные остатки. Без них сверка не сойдётся никогда:
#    позиции уйдут в минус на первой же продаже бумаги, купленной до архива.
portfolio import-csv data/input/opening_balances.csv

# 2. Отчёты брокера. Файл, несколько файлов или весь архив каталогом:
#    каталог обходится в хронологическом порядке по периоду самого отчёта.
portfolio import-broker report_2025-08.html --dry-run
portfolio import-broker report_2025-08.html
portfolio import-broker data/input/архив -r

# 3. Сверка после каждого месяца, а не только в конце
portfolio check
```

## Команды

| Команда | Что делает | Код возврата |
|---|---|---|
| `portfolio init-db` | создаёт схему журнала в локальной БД SQLite | `2`, если `DATABASE_URL` не SQLite |
| `portfolio import-broker <путь…> [--dry-run] [--account CODE] [--force] [-r] [--pattern МАСКА] [--keep-going]` | сохраняет сырьё, разбирает отчёт, диффит с журналом, сверяет остатки и пишет одной транзакцией; каталог обходит по всем отчётам внутри | `1`, если сверка не сошлась или остались нераспознанные строки; `2`, если отчётов не найдено |
| `portfolio import-csv <file> [--dry-run]` | применяет декларативный CSV: новые строки пишет, изменённые сторнирует и перезаписывает | `2` при ошибке валидации файла |
| `portfolio check` | сверяет остатки **по каждому сохранённому отчёту** и прогоняет жёсткие инварианты | `1` при любом расхождении |
| `portfolio inbox` | очередь: нераспознанные строки и расхождения сверки | `1`, если очередь не пуста |

`--dry-run` печатает таблицу изменений и не пишет ничего. `--force` подтверждает
импорт при несошедшейся сверке — причина записывается в примечание к импорту.

Аргументом `import-broker` может быть файл, несколько файлов или каталог. Каталог
берётся по расширениям `.html`, `.htm`, `.xls` (`--pattern` сужает выбор, `-r`
заходит во вложенные каталоги) и импортируется **в хронологическом порядке по
периоду отчёта**, а не по имени файла: имена в архиве бывают вида
`report (12).html`, а позиции и остатки накопительны — отчёт за март после
майского даст верный итог и неверную историю. Прогон останавливается на первом
отчёте, который не сошёлся: расхождение накапливается, и разбирать его нужно с
первого. `--keep-going` проходит каталог целиком — это режим разбора, а не
загрузки.

`check` и `inbox` предназначены для cron: ненулевой код возврата — уведомление.

### Мягкий допуск на отчётах с займом бумаг

Расчёты по займу ложатся на границу месяца, и довести такой месяц до копейки
стоит дороже самой копейки. Расхождение **по деньгам** в пределах
`RECONCILE_LOAN_TOLERANCE` (по умолчанию 1 ₽) не останавливает импорт, если в
отчёте есть раздел `5.4` (A-27). Количества бумаг допуском не покрываются
никогда.

Принятое расхождение не исчезает: оно печатается отдельной таблицей и попадает
во «Входящие». Сверка сравнивает остаток, величину накопительную, поэтому
принятая копейка тащится во все следующие месяцы. Неточность займа держится на
месте; **растущая из месяца в месяц разница — это ошибка разбора**, и смотреть
на неё надо именно так. `RECONCILE_LOAN_TOLERANCE=0` возвращает строгую сверку.

### Почему `check` не хранит контрольные числа

Остатки берутся из сохранённого сырья в `data/raw/`, а не из отдельной таблицы.
Система должна полностью восстанавливаться из `data/raw/` + `data/input/` + код
(спека 5.8); контрольные числа в БД нарушили бы это свойство.

Из этого же следует, что сверка идёт по **каждому** отчёту, а не по последнему.
Сверка только на последнем отчёте маскирует взаимно компенсирующиеся ошибки:
пропущенная покупка и пропущенная продажа одной бумаги в разные месяцы дадут
верный итог и неверную историю.

    bonds.py              график платежей, НКД, YTM/YTP, дюрация, G-спред

    broker/mapping_v1.py  стадия 2: таблицы -> события
    broker/mapping_v2.py  стадия 2 для выгрузки Excel (формат архива)
  domain/                 журнал и проекции над ним
  jobs/                   оркестрация; единственное место с транзакциями
scripts/bondlab/          одноразовый трек: выгрузка с MOEX ISS, verify-yields

Направление импортов: `jobs` → `domain` → `calc`; `adapters` → `calc`. Обратных
импортов нет — проверяется `tests/test_layering.py`.

## Облигации

Параллельный трек: доходности считаются от графика платежей, данные берутся с
MOEX ISS. Ворота этапа 1 он не нарушает — всё, что здесь считается, проверяется
внешним источником независимо от вашего портфеля.

**Расчётное ядро** — `src/portfolio/calc/bonds.py`, постоянный модуль слоя
`calc/`: номинал на дату с учётом амортизации, НКД, полная цена, будущий
денежный поток, YTM и YTP (солвер Брента), дюрация Маколея и модифицированная,
текущая доходность, G-спред к кривой ОФЗ.

Правило, ради которого всё это писалось так: **неизвестный купон не равен
нулю**. У флоатера и у бумаги за горизонтом оферты будущие купоны неизвестны;
доходность к погашению по ним не показывается, показывается только доходность к
оферте (A-12). Ноль вместо плейсхолдера дал бы систематически заниженное число,
неотличимое от верного.

**Выгрузка и сверка** — `scripts/bondlab/`, код одноразовый:

```bash
export PYTHONPATH=src:scripts
python -m bondlab boards                    # перечень досок
python -m bondlab pull TQOB --limit 30      # доска + графики платежей по бумагам
python -m bondlab schedule SU26238RMFS4     # график из снапшота
python -m bondlab verify --board TQOB       # свой расчёт против биржевого
```

Подробнее: [`docs/BONDS-IMPLEMENTATION.md`](docs/BONDS-IMPLEMENTATION.md) —
разбор модулей, взаимодействия функций и форматов данных;
[`scripts/bondlab/README.md`](scripts/bondlab/README.md) — как пользоваться
командами трека.

**Что уже проверено и что нет.** Тесты работают на синтетических снапшотах в
`tests/fixtures/iss/` и проверяют проводку данных, а не конвенции Мосбиржи:
эталонные поля в фикстурах посчитаны тем же кодом, который их сверяет.
Конвенции закрываются заполнением таблицы эталонов
[`docs/BOND-REFERENCES.md`](docs/BOND-REFERENCES.md) по реальной доске и
калькулятору Мосбиржи. До этого доходности — рабочая гипотеза, а не знание, и
покупать по ним нельзя.

## Разработка

```bash
pytest                                   # 402 теста, без сети и без БД
ruff check .
mypy --strict src/portfolio/calc
mypy                                     # весь пакет
python tests/update_golden.py            # пересоздать эталоны парсера
python tests/make_iss_fixtures.py        # пересоздать синтетические снапшоты ISS
```

Тесты ходят в SQLite во временном каталоге. Боевая БД — PostgreSQL: нужен
нативный `NUMERIC`, миграции пишутся под неё.

Маркер `oracle` зарезервирован для тестов, требующих сети; в основной прогон они
не входят. Облигационный трек сеть тоже не трогает: выгрузка (`bondlab pull`)
отделена от разбора, а тесты идут по снапшотам на диске.

### Правила, которые нельзя нарушать

- **Никаких правок данных руками.** Один раз исправив расхождение прямой записью
  в БД, вы теряете весь смысл этапа. Любое исправление — через CSV или через код
  парсера.
- **Отсутствие данных не подменяется нулём** (спека 5.4). `.get(key, 0)` в
  расчётном контуре запрещён; вместо правдоподобного числа — `None` и прочерк.
- **Журнал append-only.** Исправление — сторнирующая запись плюс новая.
- **Каждое предметное решение — в [`ASSUMPTIONS.md`](ASSUMPTIONS.md)** с
  идентификатором, датой вступления в силу и списком затронутых модулей.
