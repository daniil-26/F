# Этап 1. Журнал, импорт, сверка

Рабочий документ. Читается вместе с `portfolio-spec.md` — ссылки вида «спека 3.2» указывают на её разделы.

---

## Как пользоваться

**Человеку.** Шаг 0 выполняется вручную и блокирует всё остальное. Задачи T1–T11 идут строго по порядку: каждая опирается на предыдущую. После каждой задачи — коммит с проходящими тестами.

**Агенту.** Одна задача за сессию. Не начинать следующую, пока не выполнен критерий готовности текущей. Если для выполнения не хватает факта об отчёте брокера — остановиться и спросить, а не додумывать: неверное допущение здесь портит схему данных, а не только код.

---

## Цель

`portfolio check` возвращает ноль на всём архиве отчётов брокера.

Пока это не выполнено, работа над этапом 2 не начинается (спека 5.10).

### Ключевое свойство этапа

**Ни одного сетевого запроса.** Сверка сравнивает количества бумаг и денежный остаток, а не стоимость. Цены, курсы, ISS, ЦБ — не нужны. Весь этап детерминирован: HTML на входе, БД на выходе, сравнение с контрольными числами из того же отчёта.

Это делает всё тестируемым офлайн. Не растрачивать.

---

## Что не пишется на этом этапе

Запреты жёсткие. Нарушение любого означает, что этап поехал.

- обращения к ISS, ЦБ РФ, любым внешним API;
- цены, рыночная стоимость, `daily_nav`;
- любые доходности (TWR, XIRR, YTM);
- облигационная логика: НКД, графики платежей, амортизация, оферты;
- вклады;
- веб-интерфейс;
- рейтинги, секторы, эмитенты;
- прогнозы.

`calc/bonds.py` разрешается писать параллельно — оно не зависит от журнала и проверяется по внешним эталонам. Но в критерий завершения этапа не входит и задерживать его не должно.

Отсутствие интерфейса три-четыре недели неприятно. Компенсация — `rich`-таблица по результату `check`. Она полезнее: смотреть будете на расхождения, а не на красивые итоги.

## Шаг 0. Разведка отчёта

**Выполняется человеком до первой строки кода.** Результат — заполненные фикстуры и записи в `ASSUMPTIONS.md`.

Открыть 3–4 отчёта разных лет и ответить:

| Вопрос | Что определяет |
|---|---|
| Есть ли номер сделки брокера? | схему `natural_key` (спека 3.2) |
| Есть ли дата расчётов отдельно от даты сделки? | нужен ли вывод `settlement_date` из календаря |
| Купоны и дивиденды — gross или net? Налог отдельной строкой? | правило расщепления в парсере |
| Комиссии одной суммой или по типам? | возможность разбора по видам |
| Есть ли остатки на конец периода — по бумагам и по деньгам? | возможна ли сверка вообще |
| Какие типы операций встречаются **за всю историю**? | объём `mapping_v1` |

Последний пункт собирается по всем отчётам архива, не по последнему. Иначе парсер будет написан под шесть типов, а в архиве их двадцать пять, и это выяснится на середине бэкфилла.

### Решения, закрываемые здесь

Записать в `ASSUMPTIONS.md` с идентификаторами:

- вариант построения `natural_key`;
- сплиты применяются проекцией `positions.py` или пишутся событием (спека, примечания);
- признание купона по дате выплаты или начисления;
- правило определения `settlement_date`, если её нет в отчёте.

### Фикстуры

Подготовить обезличенные отчёты в `tests/fixtures/`:

1. самый ранний доступный (формат мог отличаться);
2. месяц с максимальным разнообразием операций;
3. месяц с корпоративным действием, если есть;
4. месяц с частичным исполнением заявки, если найдётся.

Для каждого — файл ожидаемого результата: список операций и контрольные остатки.

## Задачи

### T1. Каркас

`pyproject.toml`, `docker-compose.yml` (PostgreSQL + приложение), `config.py`, `db.py`, alembic.

Настройки: ruff, mypy строгий на `calc/`, pytest с маркером `oracle` для тестов, требующих сети.

**Готово:** `docker compose up` поднимает БД, пустой alembic-апгрейд проходит, `pytest` запускается.

---

### T2. `adapters/formats.py`

Разбор строк источника: русские числа (неразрывный пробел `\xa0`, обычный пробел, запятая как десятичный разделитель), даты, коды валют.

Маленький модуль, но от него зависит всё, и ошибка даёт тихую порчу сумм.

**Готово:** юнит-тесты на всех вариантах написания чисел из реальных фикстур; property-тест на обратимость разбора и форматирования.

---

### T3. `calc/money.py`, минимальная часть

Только то, что нужно этапу:

```python
class Money:  # (Decimal, currency)
    # конструктор бросает на float — не приводит
    # +, − только одной валюты
    # * и / на Decimal
    # Money * Money не определено

def money_sum(items: Iterable[Money]) -> Money: ...   # с проверкой валют
def is_close(a: Money, b: Money, tol: Money) -> bool: ...
def round_amount(m: Money) -> Money: ...              # до копейки, ROUND_HALF_UP
```

`convert` не нужен — курсов на этапе нет. Распределение остатка не нужно — амортизаций нет.

**Готово:** попытка создать `Money` из `float` падает; сложение разных валют падает; тесты округления.

---

### T4. `models.py` и первая миграция

Таблицы этапа: `accounts`, `instruments`, `transactions`, `raw_reports`.

**Асимметрия обязательна:**

- `transactions` — **полная схема по спеке 3.2 сразу**, включая поля, которые останутся пустыми (`cbr_rate`, `predecessor_id`). Менять схему журнала потом дорого;
- `instruments` — **минимальный**: тикер, ISIN, тип, валюта. Без эмитентов, секторов, графиков.

`natural_key` — UNIQUE-индекс в БД, не проверка в коде.

**Готово:** миграция применяется и откатывается; `alembic check` чист.

---

### T5. `adapters/broker/tables.py`

Стадия 1 парсера: `bytes` → список таблиц как есть. Заголовки, строки, ячейки строками. Не знает про сделки и купоны.

**Готово:** golden-тест на фикстурах — количество таблиц, их заголовки, размерности. Меняться дальше почти не будет.

---

### T6. `anchors.py` и `mapping_v1.py`

**Самая объёмная задача этапа, примерно половина времени.**

`anchors.py` — соответствие «текст заголовка секции → логическое имя». Поиск по подписи, не по индексу.

`mapping_v1.py` — таблицы → `ParsedOperation`. Отображение колонок, распознавание типа операции, отбрасывание строк «Итого» и подзаголовков.

Здесь же:
- **расщепление gross/net**: суммы в журнал всегда до налога, удержание отдельным событием `TAX`. Если gross не восстанавливается — `withheld_at_source = unknown`, вычислять делением на (1 − ставка) запрещено (спека 3.2);
- **разбор комиссий по типам** (брокерская, депозитарная, за вывод), не одной суммой.

DTO:

```python
@dataclass(frozen=True)
class ParsedOperation:
    kind: str                 # строкой, маппинг в EventType — в domain
    trade_date: date
    settlement_date: date | None
    ticker: str | None        # не instrument_id
    quantity: Decimal | None
    price: Decimal | None
    amount: Decimal
    currency: str
    fee_kind: str | None
    broker_trade_no: str | None
    withheld_at_source: bool | None
    raw_row: dict             # для разбора расхождений

@dataclass(frozen=True)
class ParsedBalance:
    kind: str                 # cash | security
    ticker: str | None
    quantity: Decimal
    currency: str

@dataclass(frozen=True)
class UnparsedRow:
    table: str
    row: dict
    reason: str
```

Контракт парсера:

```python
def parse_report(content: bytes) -> tuple[
    list[ParsedOperation], list[ParsedBalance], list[UnparsedRow]
]: ...
```

**Функция не пишет в БД и не сохраняет файл.** Благодаря этому golden-тесты работают без БД и без сети.

Работа итеративная: прогнать по архиву → собрать `UnparsedRow` → добавить правила → повторить.

**Готово:** пустой список нераспознанного на всех отчётах архива; golden-тесты на фикстурах проходят.

---

### T7. `domain/`

По порядку зависимостей.

**`events.py`** — перечисление типов (спека 3.2), признак «внешний / внутренний» как свойство типа, построение `natural_key` по выбранному в шаге 0 варианту.

Если используется порядковый индекс: считается **в пределах календарного дня, а не отчёта**, иначе перекрытие периодов ломает ключ.

**`raw.py`** — сохранение файла в `data/raw/`, хеш, защита от повторной загрузки, версия парсера.

**`instruments.py`** — разрешение тикеров и ISIN в `instrument_id`, создание недостающих записей.

**`ledger.py`** — запись событий, идемпотентность по `natural_key`, дифф входного набора с журналом, генерация сторно.

**`positions.py`** — **только количества и лоты, без оценки**. Дата и цена каждой партии сохраняются (нужны позже для FIFO и ЛДВ), рыночная стоимость не считается.

**`reconcile.py`** — сравнение расчётных остатков с `ParsedBalance`. Деньги сверяются по `settlement_date`, бумаги по `trade_date`.

**`invariants.py`** — жёсткие проверки, доступные без цен (см. таблицу ниже). Возвращают список нарушений, падает вызывающая сторона.

**`inbox.py`** — минимальный: нераспознанные строки и расхождения сверки.

**Готово:** юнит-тесты на каждый модуль; `test_invariants.py` — каждый инвариант срабатывает на подготовленном нарушении.

---

### T8. `jobs/import_broker.py`

Оркестрация. Единственное место с транзакцией.

```
сохранить сырьё с хешем        raw.py
распарсить                     adapters/broker
разрешить тикеры               instruments.py
построить natural_key          events.py
сдиффить с журналом            ledger.py
сверить остатки                reconcile.py
── граница --dry-run ──
записать одной транзакцией     ledger.py
```

`--dry-run` останавливается перед последним шагом и печатает, что было бы записано.

**Готово:** `test_idempotency.py` — двойной импорт одного файла не меняет журнал; два отчёта с перекрывающимся периодом дают корректный результат; отчёт с частичным исполнением заявки разбирается в две операции.

---

### T9. `jobs/import_csv.py` и начальные остатки

`opening_balances.csv` с колонками `id`, счёт, инструмент, количество, `cost_basis`, `basis_quality`, примечание.

**Без начальных остатков сверка не сойдётся никогда**: позиции уйдут в минус на первой же продаже бумаги, купленной до начала архива.

Дифф по колонке `id`, генерация сторно при изменении строки. Механизм проверяется на самом простом файле — потом тот же код обслуживает вклады и денежные потоки.

`cash_flows.csv` — здесь же, если довнесения не видны из отчёта брокера.

**Готово:** правка строки в CSV даёт сторно плюс новую запись, а не удаление; повторный импорт без изменений не пишет ничего.

### T11. Бэкфилл

Импорт всего архива в хронологическом порядке, `check` после каждого месяца.

**Первый прогон провалится. Это запланировано** — именно он и есть настоящий тест парсера. Разбор расхождений и есть основная работа задачи.

Частые причины, в порядке вероятности:

1. неучтённый тип комиссии — депозитарная обычно приходит отдельной строкой в неожиданном месте;
2. операции в последний торговый день месяца из-за T+1;
3. корпоративные действия в архиве: конвертации, сплиты, редомициляция;
4. купон нетто там, где ожидался брутто;
5. начальные остатки заполнены неполно.

**Ранние отчёты могут быть в другом формате.** Тогда `mapping_v0` для старых, `mapping_v1` для новых, выбор по дате отчёта. Механизм версионирования пригодится сразу.

## Правила работы

**Никаких правок данных руками.** Один раз исправив расхождение прямой записью в БД, вы теряете весь смысл этапа. Любое исправление — через CSV или через код парсера.

**Отсутствие данных не подменяется нулём** (спека 5.4). `.get(key, 0)` в расчётном контуре запрещено.

**Направление импортов:** `jobs` → `domain` → `calc`; `adapters` → `calc`. Обратных нет.

**Транзакции открываются только в `jobs/`.**

**`calc/` не знает текущей даты** — всё, зависящее от «сегодня», приходит аргументом.

**Каждое предметное решение — в `ASSUMPTIONS.md`** с идентификатором, датой вступления в силу и списком затронутых модулей.

---

## Готовность этапа

- [ ] весь архив импортирован в хронологическом порядке;
- [ ] `check` возвращает ноль **после каждого месяца**, не только после последнего;
- [ ] список нераспознанных строк пуст на всех отчётах;
- [ ] повторный импорт любого отчёта не меняет журнал;
- [ ] два отчёта с перекрывающимся периодом обрабатываются корректно;
- [ ] частичное исполнение заявки разбирается в две операции;
- [ ] golden-тесты на фикстурах проходят;
- [ ] `ASSUMPTIONS.md` содержит закрытые решения из шага 0;
- [ ] `ruff`, `mypy --strict src/portfolio/calc`, `pytest` — чисто.

Требование «после каждого месяца» важнее остальных. Сверка только на последнем отчёте маскирует взаимно компенсирующиеся ошибки: пропущенная покупка и пропущенная продажа одной бумаги в разные месяцы дадут верный итог и неверную историю.
